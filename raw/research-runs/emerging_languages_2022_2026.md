### Hylo

- **Website / repo:** [hylo-lang.org](https://hylo-lang.org/), [github.com/hylo-lang/hylo](https://github.com/hylo-lang/hylo)
- **Summary:** Hylo is "a programming language that leverages mutable value semantics and generic programming for high-level systems programming" ([Hylo introduction](https://hylo-lang.org/introduction/)). It is positioned as "a zero-cost abstraction language that fully acknowledges the physical constraints of computer architecture" while still presenting a value-oriented user model ([Hylo introduction](https://hylo-lang.org/introduction/)). Its lineage is explicitly Swift-derived: "Hylo borrows heavily from Swift which has demonstrated a user-friendly approach to generic programming and deep support for value semantics," while "de-emphasizing reference semantics and avoiding the complexities that result from trying to make it statically safe (e.g., memory regions, lifetime annotations, etc.)" ([Hylo introduction](https://hylo-lang.org/introduction/)). The site names Rust, Zig and Vale as overlapping efforts ([Hylo introduction](https://hylo-lang.org/introduction/)). The developing organization is not named on the official site; the compiler is "open source and hosted on GitHub" ([Hylo introduction](https://hylo-lang.org/introduction/)).
- **Most distinctive idea:** "What sets Hylo apart in the current landscape is its focus on mutable value semantics for the purpose of writing efficient, generic code" ([Hylo introduction](https://hylo-lang.org/introduction/)) — the surface language is built on values with in-place mutation instead of a reference/lifetime discipline. The homepage banner states the same commitment: "All in on Value Semantics and Generic Programming" ([hylo-lang.org](https://hylo-lang.org/)).
- **Maturity:**
  - Release stage: **research prototype / pre-alpha.** "Hylo is under active development and is not ready to be used yet" ([Hylo introduction](https://hylo-lang.org/introduction/)); "the compiler and standard library are still in their early stages" ([hylo-lang.org](https://hylo-lang.org/)). The only tag published on the repository is `v-old-0.0.42`, published 2026-05-14 ([hylo-lang/hylo releases](https://github.com/hylo-lang/hylo/releases)).
  - Activity in 2026: **active but slowed** — repository last pushed 2026-09-07, most recent commit on the default branch 2026-07-13, 1,558 stars ([hylo-lang/hylo](https://github.com/hylo-lang/hylo)).
- **Relevance to AI-agent-written code:** Mutable value semantics removes the single hardest thing for a code generator to get right in Rust-style systems languages — aliasing and lifetime annotations — because there are no reference types to annotate in the surface language. An agent can emit straightforward value-passing code and the compiler still rejects the aliasing violations that would be memory-unsafety in C++. The downside is corpus size: Hylo is pre-alpha with a tiny public code corpus, so agents have little idiomatic material to imitate and will hallucinate syntax that does not exist. Its Swift lineage partially mitigates this, since Swift-shaped generics and value semantics are well represented in training data.

### Roc

- **Website / repo:** [roc-lang.org](https://www.roc-lang.org/), [github.com/roc-lang/roc](https://github.com/roc-lang/roc)
- **Summary:** Roc describes itself as "A fast, friendly, functional language" whose "syntax, semantics, and included toolset all prioritize user-friendliness" ([roc-lang.org](https://www.roc-lang.org/)). It compiles ahead of time: "Roc code is designed to build fast and run fast. It compiles to machine code or WebAssembly" ([roc-lang.org](https://www.roc-lang.org/)). Governance sits with the Roc Programming Language Foundation, "a registered US 501(c)(3) nonprofit organization," with Richard Feldman as the principal contributor and Lambda Class, ohne-makler and Martian as corporate sponsors ([roc-lang.org](https://www.roc-lang.org/)). The site is candid about scale: "We are a small group trying to do big things" ([roc-lang.org](https://www.roc-lang.org/)).
- **Most distinctive idea:** Roc's compiler is deployable as a pure-frontend artifact — "You can run the full compiler in the browser without a backend server!" ([roc-lang.org](https://www.roc-lang.org/)) — and the site's examples are "built and tested with the same Roc compiler as this website" ([roc-lang.org](https://www.roc-lang.org/)). The official pages fetched do not name a single distinctive semantic idea beyond friendliness and fast native/Wasm compilation, so a stronger claim would be unsupported.
- **Maturity:**
  - Release stage: **alpha.** "Roc is a Work in Progress!" ([Roc install page](https://www.roc-lang.org/install)). The most recent published release channel is `alpha4-rolling`, published 2025-08-26; earlier channels are `alpha3-rolling` (2025-02-26) and `0.0.0-alpha1` (2025-01-29) ([roc-lang/roc releases](https://github.com/roc-lang/roc/releases)).
  - Activity in 2026: **very active** — repository last pushed 2026-09-12 with a commit on the default branch the same day (2026-09-12), 6,043 stars ([roc-lang/roc](https://github.com/roc-lang/roc)).
- **Relevance to AI-agent-written code:** A deliberately small, one-obvious-way functional language with ahead-of-time compilation is a good fit for agent generation: fewer constructs means fewer opportunities to hallucinate, and a compile step catches type errors before anything runs. The browser-embeddable compiler is directly useful for agent loops, since an agent can typecheck candidate programs without provisioning a toolchain. The main hindrance is churn: an alpha language whose semantics are still moving means agent-generated code trained on older snapshots will not compile.

### Koka

- **Website / repo:** [koka-lang.github.io/koka](https://koka-lang.github.io/koka/doc/book.html), [github.com/koka-lang/koka](https://github.com/koka-lang/koka)
- **Summary:** Koka is "a strongly typed functional-style language with effect types and handlers" that "separates pure values from side-effecting computation" ([Koka book](https://koka-lang.github.io/koka/doc/book.html)). The book is authored by Daan Leijen and dated 2026-03-17, and the design rests on a chain of Microsoft Research technical reports including "Generalized Evidence Passing for Effect Handlers," "Reference Counting with Frame Limited Reuse" (MSR-TR-2021-30) and "FP²: Fully in-Place Functional Programming" (MSR-TR-2023-19) ([Koka book](https://koka-lang.github.io/koka/doc/book.html)). It targets the standard memory-management dilemma directly: manual management gives "the best performance but at a significant programming burden," while garbage collection means "a runtime system and pay a price in performance, memory usage, and unpredictable latencies" ([Koka book](https://koka-lang.github.io/koka/doc/book.html)). Koka "distinguishes itself through effect typing, effect handlers, and Perceus memory management" ([Koka book](https://koka-lang.github.io/koka/doc/book.html)).
- **Most distinctive idea:** Whole-program effect inference — "Koka infers and tracks the effect of every function in its type" and "automatically infers all the side effects that occur in a function," giving "deep safety guarantees backed by well-studied category theory" ([Koka book](https://koka-lang.github.io/koka/doc/book.html)). Effects tracked include exceptions, divergence, console, non-determinism, mutability, I/O and user-defined control effects ([Koka book](https://koka-lang.github.io/koka/doc/book.html)).
- **Maturity:**
  - Release stage: **pre-1.0 research language, actively released.** Latest published release `v3.2.3`, published 2026-03-18 ([koka-lang/koka releases](https://github.com/koka-lang/koka/releases)).
  - Activity in 2026: **active, moderately paced** — repository last pushed 2026-08-15 with the most recent `dev`-branch commit 2026-08-15, 4,058 stars ([koka-lang/koka](https://github.com/koka-lang/koka)).
- **Relevance to AI-agent-written code:** Koka is close to an ideal target for auditing agent output, because effects are not merely documented but inferred into the type: if a generated function touches I/O or mutates state, that fact appears in its signature whether or not the agent intended it. A reviewer or a policy checker can therefore reject generated code that acquired an unexpected effect without reading the body. Perceus reference counting also removes GC-pause reasoning from the agent's plate while keeping deterministic deallocation. Against this, row-polymorphic effect types are unusual enough that agents frequently produce plausible-but-ill-typed effect rows.

### Austral

- **Website / repo:** [austral-lang.org](https://austral-lang.org/spec/spec.html), [github.com/austral/austral](https://github.com/austral/austral)
- **Summary:** Austral is a "Systems language with linear types and capability-based security" ([austral/austral](https://github.com/austral/austral)). Its author frames linearity as the mechanism for safe manual memory: "Linear types let us have manual memory management, without runtime overhead, and without security vulnerabilities: they prevent memory leaks, use-after-free, and double-free errors" ([Introducing Austral](https://borretti.me/article/introducing-austral)). The idea generalizes past memory: "This extends beyond memory to anything that has a lifecycle... File handles, network sockets, database handles, locks and mutexes: the correct usage of these objects can be enforced at compile time" ([Introducing Austral](https://borretti.me/article/introducing-austral)). It also targets supply-chain risk — "an attacker adds malware to a single library used transitively by millions of computers" — with the position that "to access the filesystem, or the network, or other privileged resources, libraries should require permission to do so," and "Austral's solution is capability-based security" ([Introducing Austral](https://borretti.me/article/introducing-austral)). The project is developed by an individual (GitHub user `eudoxia0`) rather than an organization ([austral/austral releases](https://github.com/austral/austral/releases)).
- **Most distinctive idea:** Linear types plus capability-based security in one systems language, so that both resource lifecycles and module permissions are compile-time facts; a design goal is explicitly to eliminate ambiguity, since "language lawyering is a design flaw: if two people can look at the same basic program and disagree about its behaviour, that's" a defect ([Introducing Austral](https://borretti.me/article/introducing-austral)).
- **Maturity:**
  - Release stage: **pre-1.0, feature-complete core.** Latest release `v0.2.0`, published 2023-06-27; the `0.1.0` release is titled "Core language complete," and `0.2.0` realigned borrow syntax with the rest of the language ([austral/austral releases](https://github.com/austral/austral/releases)).
  - Activity in 2026: **dormant** — no 2026 activity; the repository was last pushed 2025-07-28 and the most recent commit is 2025-07-28, 1,573 stars ([austral/austral](https://github.com/austral/austral)).
- **Relevance to AI-agent-written code:** Austral is unusually well matched to constraining generated code, and its author noticed this early — the introduction post records plans to "use OpenAI's finetuning API to teach a code completion model to write Austral for me" and reports "promising results teaching Austral to ChatGPT interactively" ([Introducing Austral](https://borretti.me/article/introducing-austral)). Capabilities mean a generated module physically cannot open a socket unless it was handed that permission, which is a far stronger containment story than sandboxing generated code after the fact. Linearity turns forgotten `close()` calls — a classic LLM omission — into compile errors. The practical obstacle is that the project is dormant, so there is neither a maintained toolchain nor a growing corpus.

### Inko

- **Website / repo:** [inko-lang.org](https://inko-lang.org/), [github.com/inko-lang/inko](https://github.com/inko-lang/inko)
- **Summary:** Inko is "a programming language for building concurrent software, but without the usual headaches such as data race conditions and non-deterministic garbage collectors" ([Inko 0.19.1 release notes](https://inko-lang.org/news/inko-0-19-1-is-released/)). It "features deterministic automatic memory management" and "compiles to machine code using LLVM" for Linux, macOS and FreeBSD ([Inko 0.19.1 release notes](https://inko-lang.org/news/inko-0-19-1-is-released/)). Memory is managed by single ownership: "Single ownership is a way of managing memory by assigning owners to values, and discarding... of these values when the owner is done with them," which means memory management "is deterministic and predictable, and doesn't require a garbage collector or (atomic) reference counting" ([Inko 0.10.0 release notes](https://inko-lang.org/news/inko-0-10-0-released/)). Concurrency is Erlang-derived: "Inspired by Erlang, Inko uses lightweight isolated threads known as 'lightweight processes'. These processes don't share memory and communicate by sending messages" ([Inko 0.10.0 release notes](https://inko-lang.org/news/inko-0-10-0-released/)). Development is self-funded rather than corporate ([Inko 0.19.1 release notes](https://inko-lang.org/news/inko-0-19-1-is-released/)).
- **Most distinctive idea:** Single ownership combined with isolated message-passing processes, but with an aliasing rule deliberately looser than Rust's: "Unlike Rust, Inko allows you to have both mutable and immutable references to the same value at the same time" ([Inko 0.10.0 release notes](https://inko-lang.org/news/inko-0-10-0-released/)); values sent between processes are moved, "no longer available to the sender" ([Inko 0.10.0 release notes](https://inko-lang.org/news/inko-0-10-0-released/)).
- **Maturity:**
  - Release stage: **pre-1.0 alpha/beta.** Version 0.10.0 (2022) was the major redesign — released after "almost two years since the last Inko release" and "1.5 years since we started work on drastically changing Inko"; the project states "Inko is only at version 0.10, and we still have a long road ahead of us before reaching version 1.0" and warns of "bugs, compiler crashes, performance issues, or missing/lacking documentation" ([Inko 0.10.0 release notes](https://inko-lang.org/news/inko-0-10-0-released/)). Version 0.19.1 is documented on the site ([Inko 0.19.1 release notes](https://inko-lang.org/news/inko-0-19-1-is-released/)); no GitHub Releases entries are published for the repository ([inko-lang/inko](https://github.com/inko-lang/inko)).
  - Activity in 2026: **active** — repository last pushed 2026-09-11, most recent commit 2026-09-05, 1,302 stars ([inko-lang/inko](https://github.com/inko-lang/inko)).
- **Relevance to AI-agent-written code:** Isolated processes with move-on-send semantics remove most of the concurrency reasoning an agent would otherwise have to do by hand: there is no shared mutable state to protect, so no lock ordering to get wrong. Deterministic, GC-free memory management also makes generated code's resource behavior predictable enough to test. The looser aliasing rule than Rust's is a mixed blessing — it makes generated code compile more often, but it means some correctness reasoning the Rust borrow checker would perform has to happen elsewhere. Its pre-1.0 status and small corpus remain the practical limit.

### Gleam

- **Website / repo:** [gleam.run](https://gleam.run/), [github.com/gleam-lang/gleam](https://github.com/gleam-lang/gleam)
- **Summary:** Gleam is a friendly, statically typed language that runs "on the Erlang virtual machine" and can also target "JavaScript runtimes," with "a type system inspired by languages such as Elm, OCaml, and Rust" ([Gleam version 1](https://gleam.run/news/gleam-version-1/)). Its stated goal is to make software development and maintenance "as predictable, stress-free, and enjoyable as possible," optimizing for reading and debugging rather than writing: "Reading and debugging code is more difficult than writing new code, so we optimise for this" ([Gleam version 1](https://gleam.run/news/gleam-version-1/)). It is explicitly not a big-tech project — "Gleam is not a project from Microsoft or Google, it's a community project" — with "one full-time developer working on Gleam... and a number of part time volunteers," funded via GitHub Sponsors, of which "the largest contributor is Fly.io, who provide approximately half the funding" ([Gleam version 1](https://gleam.run/news/gleam-version-1/)).
- **Most distinctive idea:** Enforced minimalism as a language-design commitment — "a strong desire to have only one way of doing things," with the explicit statement that "Simplicity is a feature in Gleam and that will not change going forward" ([Gleam version 1](https://gleam.run/news/gleam-version-1/)), and the consequence that "with Gleam refactoring is low risk and low stress" ([Gleam version 1](https://gleam.run/news/gleam-version-1/)).
- **Maturity:**
  - Release stage: **1.0+ / stable.** "Today Gleam v1.0.0 has been released!... This is the first 'stable' release of the language" ([Gleam version 1](https://gleam.run/news/gleam-version-1/)), dated 04 March, 2024 ([Gleam news index](https://gleam.run/news/)). The most recent minor release listed is v1.18.0 on 29 July, 2026 ([Gleam news index](https://gleam.run/news/)), with `v1.18.1` published 2026-08-01 ([gleam-lang/gleam releases](https://github.com/gleam-lang/gleam/releases)).
  - Activity in 2026: **very active** — repository last pushed 2026-09-10, most recent commit 2026-09-10, 21,904 stars ([gleam-lang/gleam](https://github.com/gleam-lang/gleam)).
- **Relevance to AI-agent-written code:** "Only one way of doing things" is arguably the single most agent-friendly property a language can have: a small regular grammar with no competing idioms narrows the space in which a model can hallucinate, and reduces the variance between what the agent writes and what a reviewer expects. Full static typing over the BEAM means generated concurrent code gets checked rather than merely hoped for. The main cost is ecosystem depth relative to Elixir or TypeScript, so agents will more often need to write library code from scratch instead of calling something existing.

### Unison

- **Website / repo:** [unison-lang.org](https://www.unison-lang.org/), [github.com/unisonweb/unison](https://github.com/unisonweb/unison)
- **Summary:** Unison is a statically typed functional language whose codebase is a database of content-addressed definitions rather than a directory of text files ([The big idea](https://www.unison-lang.org/docs/the-big-idea/)). Every definition has "a unique and deterministic address (its hash) in this vast immutable address space. Names are like pointers to addresses in this space," and "Names are just separately stored metadata that don't affect the function's hash" ([The big idea](https://www.unison-lang.org/docs/the-big-idea/)). This targets distributed programming, which today requires "many separate programs stitched together with a morass of glue, duct tape, YAML files, and blobs of JSON being sent over the network" ([The big idea](https://www.unison-lang.org/docs/the-big-idea/)). Consequences claimed include that "dependency conflicts and the diamond dependency problem are just not a thing," that "arbitrary computations [can] just be moved from one location to another, with missing dependencies deployed on the fly," and that "a Unison codebase is never in a broken state, even midway through a refactoring" ([The big idea](https://www.unison-lang.org/docs/the-big-idea/)).
- **Most distinctive idea:** Content-addressed code: "Definitions never change" and "the hash of `increment` uniquely identifies its exact implementation and pins down all its dependencies" ([The big idea](https://www.unison-lang.org/docs/the-big-idea/)), which is what makes instant non-breaking renames, type-based search and hyperlinked code possible ([The big idea](https://www.unison-lang.org/docs/the-big-idea/)).
- **Maturity:**
  - Release stage: **1.0+.** "After years of engineering, design, and community collaboration, we're excited to release Unison 1.0. This version delivers a refined programming workflow and a mature toolchain" ([Unison blog](https://www.unison-lang.org/blog/)); `release/1.0.0` was published 2025-11-25 and the latest release is `release/1.4.0`, published 2026-08-19 ([unisonweb/unison releases](https://github.com/unisonweb/unison/releases)).
  - Activity in 2026: **active** — repository last pushed 2026-08-19 with the most recent commit 2026-08-19, 6,725 stars ([unisonweb/unison](https://github.com/unisonweb/unison)).
- **Relevance to AI-agent-written code:** Content addressing directly removes the failure modes that dominate LLM-written code at scale: there are no stale imports, no version-resolution conflicts, and no partially-broken intermediate states during refactoring, because a definition is identified by its hash rather than by a name the agent has to remember correctly ([The big idea](https://www.unison-lang.org/docs/the-big-idea/)). Type-based search gives an agent a mechanical way to find an existing function instead of inventing one. Notably, the project has begun shipping agent-facing tooling: 1.1.0 "contains new MCP tools" and 1.0.2 improved "the MCP AI agent commands" ([Unison blog](https://www.unison-lang.org/blog/)). The offsetting cost is that the codebase-as-database model is unlike anything in training corpora, so agents must be taught the UCM workflow rather than inferring it.

### Mojo

- **Most distinctive idea:** n.a. — the primary pages fetched (the 1.0 forum announcement and the launch blog) do not state a single distinctive design idea; the 1.0 post explicitly covers stability commitments rather than semantics ([Mojo 1.0 is here](https://forum.modular.com/t/mojo-1-0-is-here/3391)).

Mojo 1.0 shipped as part of MAX 26.5 on August 11, 2026 ([Modular blog](https://www.modular.com/blog/mojo-its-finally-here)); the corresponding tag `max/v26.5.0` ("MAX 26.5 / Mojo 1.0.0") was published 2026-08-11, preceded by `max/v26.4.0` ("Mojo 1.0.0b2", 2026-06-18) and `max/v26.3.0` ("Mojo 1.0.0b1", 2026-05-07) ([modular/modular releases](https://github.com/modular/modular/releases)).

That combination — high generation success rate and a strict rejection filter — is what agent workflows want. The risk is the inverse of the same property: because Mojo looks like Python, agents readily emit valid Python that is not valid Mojo, and the 1.x additive-change policy ([Mojo 1.0 is here](https://forum.modular.com/t/mojo-1-0-is-here/3391)) will only slowly reduce that confusion.

### MoonBit

- **Website / repo:** [moonbitlang.com](https://www.moonbitlang.com/), [github.com/moonbitlang/core](https://github.com/moonbitlang/core)
- **Summary:** MoonBit describes itself as "a programming language designed for tooling *(AI focused)* and user experience," with "robust and extremely fast tooling" ([MoonBit beta release](https://www.moonbitlang.com/blog/beta-release)). Feature-wise it positions itself against Rust: "it is very close to Rust with GC but shipped with robust and extremely fast tooling" ([MoonBit beta release](https://www.moonbitlang.com/blog/beta-release)). It builds async and error handling into ordinary function syntax: "Async and error-aware functions are written just like regular ones—no `await`, no extra syntax" ([MoonBit beta release](https://www.moonbitlang.com/blog/beta-release)). It also "treats pattern matching as a first-class feature" ([MoonBit 1.0 roadmap](https://www.moonbitlang.com/blog/roadmap)). The developing organization is not named on the fetched official pages.
- **Most distinctive idea:** Designing the language *for* AI tooling as a first-order requirement rather than a downstream concern — "a programming language designed for tooling *(AI focused)* and user experience" — paired with effect-free-looking syntax for async and checked errors, so that "async and error-aware functions are written just like regular ones" ([MoonBit beta release](https://www.moonbitlang.com/blog/beta-release)).
- **Maturity:**
  - Release stage: **beta.** "The Beta release marks a clear commitment: MoonBit's core language features are now stable," syntax "is considered stable and changes will go through RFC process," while "the standard library and toolchain will continue to improve" and "async and checked error handling are in beta" ([MoonBit beta release](https://www.moonbitlang.com/blog/beta-release)). "In June 2025, MoonBit released its beta version" and "We are planning to officially launch version 1.0 in the first half of 2026" ([MoonBit 1.0 roadmap](https://www.moonbitlang.com/blog/roadmap)); as of September 2026 no 1.0 announcement was found on the official blog. Specific version-number-with-date for the current release: n.a.
  - Activity in 2026: **very active** — the core library repository was last pushed 2026-09-12 with the most recent commit 2026-09-12, 1,205 stars ([moonbitlang/core](https://github.com/moonbitlang/core)).
- **Relevance to AI-agent-written code:** MoonBit is the clearest case in this survey of a language whose stated purpose includes machine authorship ([MoonBit beta release](https://www.moonbitlang.com/blog/beta-release)), and the design choices follow from it: fast compilation gives agents a tight generate-check loop, and eliminating `await` and error-propagation ceremony removes two of the most common syntactic mistakes models make in Rust and TypeScript. First-class pattern matching ([MoonBit 1.0 roadmap](https://www.moonbitlang.com/blog/roadmap)) also pushes generated code toward total, exhaustively-checked case analysis rather than defensive `if` chains. The counterweight is that "close to Rust with GC" means agents will import Rust idioms (lifetimes, `unsafe`, trait patterns) that do not apply.

### Verse

- **Website / repo:** [verselang.github.io/book](https://verselang.github.io/book/00_overview/), [dev.epicgames.com Verse reference](https://dev.epicgames.com/documentation/en-us/fortnite/verse-language-reference)
- **Summary:** "Verse is a multi-paradigm programming language developed by Epic Games" for "creating gameplay in Unreal Editor for Fortnite and building experiences in the metaverse" ([Book of Verse overview](https://verselang.github.io/book/00_overview/)). It draws "from functional, logic, and imperative traditions" and is framed as "a departure from traditional programming languages" that "carry decades of historical baggage and design compromises" ([Book of Verse overview](https://verselang.github.io/book/00_overview/)). Its design constraints come from the premise that "code runs in a single global simulation—the metaverse," where "code lives forever in a persistent metaverse," "millions of developers contribute to a shared codebase," "backward compatibility is not optional but essential," and "the boundary between compile-time and runtime is fluid" ([Book of Verse overview](https://verselang.github.io/book/00_overview/)). Epic commits to compatibility: "For Verse code that you write today, you can expect Verse to provide backward compatibility and continue to work with future updates to the language" ([Verse language reference](https://dev.epicgames.com/documentation/en-us/fortnite/verse-language-reference)).
- **Most distinctive idea:** Radical uniformity — "It's Just Code": "Complex concepts that might require special syntax or constructs in other languages are expressed as regular Verse code. There's no magic—everything is built from the same primitive constructs, creating a uniform and predictable programming model" ([Book of Verse overview](https://verselang.github.io/book/00_overview/)) — in service of code that is "safe, concurrent, and composable by default" and safe to run when "untrusted" in a shared environment ([Book of Verse overview](https://verselang.github.io/book/00_overview/)).
- **Maturity:**
  - Release stage: **production-used, versioned by language version rather than semver.** Epic documents "Verse Language Version 1 Updates and Deprecations" ([Verse language reference](https://dev.epicgames.com/documentation/en-us/fortnite/verse-language-reference)) and states "Epic Games is continuing to develop the Verse programming language and add more features" ([Verse language reference](https://dev.epicgames.com/documentation/en-us/fortnite/verse-language-reference)). Exact release date of Verse Version 1: n.a. The community Book of Verse states no version numbers or release dates ([Book of Verse overview](https://verselang.github.io/book/00_overview/)).
  - Activity in 2026: n.a. — Verse has no public primary repository; the compiler ships inside Unreal Editor for Fortnite, and no commit history was inspectable.
- **Relevance to AI-agent-written code:** Two Verse properties matter for machine authorship. First, uniformity — no special-cased syntax, everything built from the same primitives ([Book of Verse overview](https://verselang.github.io/book/00_overview/)) — is precisely the regular-grammar property that reduces hallucination. Second, the language is designed on the assumption that untrusted code from unknown authors will run in a shared live simulation ([Book of Verse overview](https://verselang.github.io/book/00_overview/)), which is structurally the same threat model as executing agent-generated code. The hard limit is closure: with no open compiler or public repository, agents cannot be evaluated against Verse outside Epic's tooling, and the public corpus is thin.

### Bend / HVM2

- **Website / repo:** [github.com/HigherOrderCO/Bend](https://github.com/HigherOrderCO/Bend), [github.com/HigherOrderCO/HVM2](https://github.com/HigherOrderCO/HVM2)
- **Summary:** "Bend is developed by HigherOrderCO" and is "A high-level, massively parallel programming language" ([HigherOrderCO/Bend](https://github.com/HigherOrderCO/Bend)). It "offers the feel and features of expressive languages like Python and Haskell," including "fast object allocations," "full support for higher-order functions with closures," "unrestricted recursion" and "even continuations" ([HigherOrderCO/Bend](https://github.com/HigherOrderCO/Bend)). Execution is delegated to a separate runtime: "Bend is powered by the HVM2 runtime," described as "HOC's massively parallel Interaction Combinator evaluator" ([HigherOrderCO/Bend](https://github.com/HigherOrderCO/Bend)), itself "a massively parallel, optimal functional runtime in Rust" ([HigherOrderCO/HVM2](https://github.com/HigherOrderCO/HVM2)). The repository was created 2023-08-29 ([HigherOrderCO/Bend](https://github.com/HigherOrderCO/Bend)).
- **Most distinctive idea:** Automatic parallelism from an interaction-combinator runtime, with no concurrency constructs in the language at all: "Bend scales like CUDA, it runs on massively parallel hardware like GPUs, with nearly linear acceleration based on core count, and without explicit parallelism annotations: no thread creation, locks, mutexes, or atomics"; "If your code **can** run in parallel it **will** run in parallel," supporting "over 10000 concurrent threads" ([HigherOrderCO/Bend](https://github.com/HigherOrderCO/Bend)).
- **Maturity:**
  - Release stage: **alpha / experimental.** The repository does not classify itself, but cautions "The current version may have lower single-core performance," "You can expect substantial improvements in performance as we advance our code generation and optimization techniques," and "We are still working to support Windows. Use WSL2 as an alternative solution" ([HigherOrderCO/Bend](https://github.com/HigherOrderCO/Bend)). Thirty-nine tags exist but no GitHub Release is published, so no version-with-date can be confirmed: n.a. ([HigherOrderCO/Bend](https://github.com/HigherOrderCO/Bend)).
  - Activity in 2026: **dormant / slowing** — Bend's repository was last pushed 2026-07-07 with the most recent commit 2026-07-07 and 19,828 stars, but the HVM2 runtime it depends on was last pushed 2024-11-21 with its most recent commit 2024-08-21, 11,342 stars ([HigherOrderCO/Bend](https://github.com/HigherOrderCO/Bend), [HigherOrderCO/HVM2](https://github.com/HigherOrderCO/HVM2)).
- **Relevance to AI-agent-written code:** Parallelism-by-default removes an entire category of reasoning from the agent: there are no threads, locks, mutexes or atomics to get wrong because none exist in the language ([HigherOrderCO/Bend](https://github.com/HigherOrderCO/Bend)). An agent writes ordinary recursive functional code and the runtime extracts the parallelism, which is a much better division of labor than asking a model to place synchronization correctly. Against that, performance is not compositional in an intuitive way — the same page warns about single-core performance and immature code generation — so an agent cannot reason about the cost of what it writes, and a stalled runtime repository makes it a poor production target.

### Carbon

If Carbon achieves bidirectional interop, agent-driven migration of C++ codebases becomes mechanically checkable file by file rather than all-at-once. The practical problem today is that there is no shipped 0.1 ([Carbon roadmap](https://github.com/carbon-language/carbon-lang/blob/trunk/docs/project/roadmap.md)), so any agent-generated Carbon is written against a moving design with essentially no corpus.

### Vale

### Flix

- **Website / repo:** [flix.dev](https://flix.dev/), [github.com/flix/flix](https://github.com/flix/flix)
- **Summary:** "Flix is a principled effect-oriented functional, imperative, and logic programming language developed at Aarhus University and by a community of open source contributors," and is "actively developed by programming language researchers from Aarhus University in Denmark in collaboration with researchers from the University of Waterloo in Canada, the University of Tübingen in Germany, and the University of Copenhagen in Denmark" ([flix.dev](https://flix.dev/)). It argues that "effect systems represent the next major evolution in statically typed programming languages," because "by explicitly modeling side effects, effect-oriented programming enforces modularity and helps program reasoning" ([flix.dev](https://flix.dev/)). It also embeds a logic-programming layer: fixpoint problems including "various graph reachability problems" are expressed through embedded Datalog ([flix.dev](https://flix.dev/)). The toolchain is monolithic by design: "Flix is one self-contained tool: compiler, build tool, package manager, test runner, and REPL" ([Flix get started](https://flix.dev/get-started/)).
- **Most distinctive idea:** A total purity guarantee backed by algebraic effects: Flix "precisely tracks the purity of every expression in a program," and "the Flix compiler provides an ironclad guarantee that if an expression is pure then it cannot have side-effects and it is referentially transparent," with "user-defined effects and handlers" letting programmers "implement their own control structures" ([flix.dev](https://flix.dev/)). Built-in effects come with defaults — "Fetching a URL uses the Http effect, so it appears in the signature. Each comes with a default handler" ([Flix get started](https://flix.dev/get-started/)).
- **Maturity:**
  - Release stage: **pre-1.0, rapidly released research language.** Latest release `v0.75.3`, published 2026-08-15, preceded by `v0.75.2` (2026-08-07) and `v0.75.1` (2026-07-09) ([flix/flix releases](https://github.com/flix/flix/releases)).
  - Activity in 2026: **very active** — repository last pushed 2026-09-12 with the most recent commit 2026-09-12, 2,739 stars ([flix/flix](https://github.com/flix/flix)).
- **Relevance to AI-agent-written code:** Flix's "ironclad guarantee" that pure expressions cannot have side effects ([flix.dev](https://flix.dev/)) turns a policy question — did the agent's code touch the network? — into a signature check, which is exactly the auditability property agent pipelines need. Because `Http` and similar effects surface in signatures ([Flix get started](https://flix.dev/get-started/)), a reviewer can gate generated code on its effect row without reading the implementation. Embedded Datalog is a further help for the class of graph/relational logic where LLMs typically write buggy imperative traversals. The friction is that effect polymorphism and Datalog-in-a-functional-language are both underrepresented in training data.

### Effekt

- **Website / repo:** [effekt-lang.org](https://effekt-lang.org/), [github.com/effekt-lang/effekt](https://github.com/effekt-lang/effekt)
- **Summary:** Effekt is "a language with lexical effect handlers and lightweight effect polymorphism" ([effekt-lang/effekt](https://github.com/effekt-lang/effekt)). Its premise is that "(algebraic) effect handlers let you define advanced control-flow structures like generators as user libraries" and that "those libraries can be seamlessly composed" ([effekt-lang.org](https://effekt-lang.org/)). It addresses two concrete failure modes of effect handlers: forgetting to handle an effect — "Effect handlers are great, but it is easy to forget handling an effect," solved by "a static effect system that tells you where you forgot to handle something" — and the ergonomics collapse in higher-order code: "often, as soon as you start writing higher-order functions the type- and effect system starts to get in your way" ([effekt-lang.org](https://effekt-lang.org/)). The site frames effect operations against a familiar mechanism: "Effect handlers are exception handlers on steroids!" and "Calling an effect operation (with `do yield(42)`) is like throwing an exception" ([effekt-lang.org](https://effekt-lang.org/)). The developing organization is not named on the homepage ([effekt-lang.org](https://effekt-lang.org/)).
- **Most distinctive idea:** "A new form of effect polymorphism, which we call **contextual effect polymorphism**" ([effekt-lang.org](https://effekt-lang.org/)), designed so that higher-order functions do not require the effect-variable plumbing that makes other effect systems unusable at scale.
- **Maturity:**
  - Release stage: **pre-1.0 research language, on a weekly release cadence.** Latest release `v0.79.0`, published 2026-08-31, preceded by `v0.78.0` (2026-08-24) and `v0.77.0` (2026-08-17) ([effekt-lang/effekt releases](https://github.com/effekt-lang/effekt/releases)).
  - Activity in 2026: **very active** — repository last pushed 2026-09-12 with the most recent commit 2026-09-12, 467 stars ([effekt-lang/effekt](https://github.com/effekt-lang/effekt)).
- **Relevance to AI-agent-written code:** The specific problem Effekt solves — a static effect system that reports "where you forgot to handle something" ([effekt-lang.org](https://effekt-lang.org/)) — maps onto a real LLM failure mode, namely generating code that raises or performs an effect with no handler anywhere in the call chain. Contextual effect polymorphism matters because the alternative (explicit effect variables threaded through every higher-order signature) is verbose boilerplate that models get wrong. The limitation is scale: at 467 stars and pre-1.0, there is almost no public Effekt corpus, so agents must work from the specification rather than by imitation.

### Ante

- **Website / repo:** [antelang.org](https://antelang.org/), [github.com/jfecher/ante](https://github.com/jfecher/ante)
- **Summary:** Ante is "a safe, easy systems language" ([jfecher/ante](https://github.com/jfecher/ante)) whose stated aim is to "help bridge the gap between low-level languages like C++/Rust and higher level garbage-collected languages like Java, OCaml, or Haskell" ([antelang.org](https://antelang.org/)). It attacks shared mutability specifically: "Shared mutability is a common cause of bugs in other languages," and Ante's type system prevents unsafe operations on mutably shared references at compile time, with the claim that "in Ante, not only is it safe, it is zero-cost" ([antelang.org](https://antelang.org/)). It carries an effect system with capability-like gating: "If a function does not declare it `can IO`, then it cannot use IO. It cannot even use external linked-in code without being allowed to do so" ([antelang.org](https://antelang.org/)). Recent site posts are authored by Jake Fecher (2024-03-17 through 2025-10-24); no sponsoring organization is named ([antelang.org](https://antelang.org/)).
- **Most distinctive idea:** "Opt-out move semantics" — "most types are not shared and use move semantics by default," but "shared types can be defined which enable cleaner code and a gentler learning curve" ([antelang.org](https://antelang.org/)) — i.e. Rust-style ownership as the default with explicitly opt-in safe shared mutability rather than an escape hatch.
- **Maturity:**
  - Release stage: **research prototype / alpha; no published release.** No GitHub Release is published for the repository, so no version-with-date can be confirmed: n.a. ([jfecher/ante](https://github.com/jfecher/ante)).
  - Activity in 2026: **active** — repository last pushed 2026-09-09 with the most recent commit 2026-09-09, 2,340 stars ([jfecher/ante](https://github.com/jfecher/ante)).
- **Relevance to AI-agent-written code:** The `can IO` capability rule is directly useful for constraining generated code: a function that has not declared the capability "cannot even use external linked-in code without being allowed to do so" ([antelang.org](https://antelang.org/)), which means an agent cannot smuggle in a shell-out or a network call without it appearing in the signature. Opt-out move semantics also raises the first-attempt compile rate relative to Rust, because the agent can reach for a shared type where lifetime gymnastics would otherwise be required, and the site notes "effects are easier to use when compared to monads" ([antelang.org](https://antelang.org/)). With no release and no corpus, however, this is currently a design argument rather than a usable workflow.

### Toka

- **Website / repo:** [tokalang.dev](https://tokalang.dev/), [arXiv:2606.01974](https://arxiv.org/abs/2606.01974) (repo: `tokalang/toka`)
- **Summary:** Toka is a systems programming language with "Explicit Resource Semantics," presented in an arXiv experience report by Zhonghua Yi ([arXiv:2606.01974](https://arxiv.org/abs/2606.01974)). It targets the fact that "systems programming languages traditionally struggle with the tension between physical transparency and compile-time memory safety," positioning itself between two poles: "C++ provides direct, zero-cost hardware access but lacks strict safety boundaries" while "Rust guarantees safety at the cost of complex lifetime annotations and implicit dereferencing chains" ([arXiv:2606.01974](https://arxiv.org/abs/2606.01974)). It supports "unique, shared, borrowed, and raw semantics" with a "lifetime checking mechanism" ([arXiv:2606.01974](https://arxiv.org/abs/2606.01974)). The site states that "no garbage collector, predictable resource costs, PAL static checking, and machine-readable, compiler-verifiable semantic evidence support this goal," and that "resource and representation costs are intended to stay visible and predictable rather than being hidden behind a default runtime layer" ([tokalang.dev](https://tokalang.dev/)). Semantics kept explicit and inspectable include ownership transfer, mutation, rebinding, nullability, error propagation, async suspension, FFI boundaries and representation-level access ([tokalang.dev](https://tokalang.dev/)).
- **Most distinctive idea:** "Handle-Soul Duality (informally referred to as the Hat-Soul model), which cleanly dissociates pointer identities (Handles) from their underlying values (Souls) at the syntactic level"; "by enforcing that bare identifiers always represent values (Souls) and explicit sigils represent pointer handles, Toka eliminates the semantic ambiguity between rebind operations and value mutations" ([arXiv:2606.01974](https://arxiv.org/abs/2606.01974)).
- **Maturity:**
  - Release stage: **research prototype.** The paper describes "its implementation of a prototype compiler" and is titled "A Design and Implementation Experience Report on Explicit Resource Semantics"; no alpha/beta/1.0 designation is given ([arXiv:2606.01974](https://arxiv.org/abs/2606.01974)). Paper v1 submitted 2026-06-01 ([arXiv:2606.01974](https://arxiv.org/abs/2606.01974)).
  - Activity in 2026: **active** — the `tokalang/toka` repository was created 2025-12-27 and last pushed 2026-09-05 ([tokalang/toka](https://github.com/tokalang/toka)).
- **Relevance to AI-agent-written code:** Toka is one of only two languages in this survey that names AI tooling in its design rationale: "the compiler exposes machine-readable semantic facts so editors and AI tools can inspect the same boundaries that developers review" ([tokalang.dev](https://tokalang.dev/)). That is a concrete answer to the verification problem for generated code — instead of an agent asserting that its code does not mutate shared state, the compiler emits verifiable evidence of that. The Handle/Soul syntactic split ([arXiv:2606.01974](https://arxiv.org/abs/2606.01974)) also removes an ambiguity that models routinely get wrong in C++ and Rust, namely whether an assignment rebinds a pointer or mutates a pointee. Being a 2026 prototype with no corpus, it currently depends on grammar-constrained generation rather than imitation.

### Pel

- **Website / repo:** [arXiv:2505.13453](https://arxiv.org/abs/2505.13453) — no separate official site found
- **Summary:** Pel is "A Programming Language for Orchestrating AI Agents" by Behnam Mohammadi ([arXiv:2505.13453](https://arxiv.org/abs/2505.13453)). It targets the problem of "controlling and orchestrating [LLMs'] capabilities beyond simple text generation," arguing that existing approaches — "function/tool calling and direct code generation" — are limited in "expressiveness, scalability, cost, security" and in "the ability to enforce fine-grained control" ([arXiv:2505.13453](https://arxiv.org/abs/2505.13453)). It is "inspired by the strengths of Lisp, Elixir, Gleam, and Haskell" and aims to provide "a syntactically simple, homoiconic, and semantically rich platform for LLMs to express complex actions, control flow, and inter-agent communication safely and efficiently" ([arXiv:2505.13453](https://arxiv.org/abs/2505.13453)). Features include "a powerful piping mechanism for linear composition," "first-class closures enabling easy partial application," "built-in support for natural language conditions evaluated by LLMs," "an advanced Read-Eval-Print-Loop (REPeL) with Common Lisp-style restarts and LLM-powered helper agents for automated error correction," and "automatic parallelization of independent operations via static dependency analysis" ([arXiv:2505.13453](https://arxiv.org/abs/2505.13453)).
- **Most distinctive idea:** Capability control implemented at the level of the grammar itself: "Pel's design emphasizes a minimal, easily modifiable grammar suitable for constrained LLM generation, eliminating the need for complex sandboxing by enabling capability control at the syntax level" ([arXiv:2505.13453](https://arxiv.org/abs/2505.13453)).
- **Maturity:**
  - Release stage: **research prototype / paper.** The abstract page does not state a maturity stage or software version ([arXiv:2505.13453](https://arxiv.org/abs/2505.13453)). Paper v1 submitted 2025-04-03, last revised 2025-06-09 (v2) ([arXiv:2505.13453](https://arxiv.org/abs/2505.13453)).

### Cangjie

### Idris 2

- **Summary:** Idris 2 is "a purely functional programming language with first class types," associated with Edwin Brady, who gave the talks "What's New in Idris 2" and "The implementation of Idris 2" ([idris-lang/Idris2](https://github.com/idris-lang/Idris2)). ### Swift 6

- **Website / repo:** [swift.org](https://www.swift.org/blog/announcing-swift-6/), [github.com/swiftlang/swift](https://github.com/swiftlang/swift)
- **Summary:** Swift 6 is a major version whose headline change reshapes the concurrency model: "Swift 6 now includes a new, opt-in language mode that extends Swift's safety guarantees to prevent data races in concurrent code by diagnosing potential data races in your code as compiler errors" ([Announcing Swift 6](https://www.swift.org/blog/announcing-swift-6/)). It also generalizes the error type system — "Swift 6 enables functions to specify the type of error that they throw as part of their signature," where "a function that is specified as `throws`... is equivalent to one that specifies `throws(any Error)`, whereas a non-throwing function is equivalent to one that specifies `throws(Never)`" ([Announcing Swift 6](https://www.swift.org/blog/announcing-swift-6/)) — and extends the ownership model into generics: "Swift 6 now supports these [non-copyable] types with the generics system, making it possible to write generic code that works with both copyable and non-copyable types" ([Announcing Swift 6](https://www.swift.org/blog/announcing-swift-6/)). Pattern matching gained ownership awareness: "switch statements can now be written to avoid copying within enum pattern-matching operations," so they "can be used with non-copyable payloads" ([Announcing Swift 6](https://www.swift.org/blog/announcing-swift-6/)). C++ interop expanded "to C++ move-only types, virtual methods, default arguments, and more standard library types including `std::map` and `std::optional`" ([Announcing Swift 6](https://www.swift.org/blog/announcing-swift-6/)).
- **Most distinctive idea:** Compile-time data-race elimination as an opt-in language mode — statically diagnosing "potential data races in your code as compiler errors" ([Announcing Swift 6](https://www.swift.org/blog/announcing-swift-6/)) — combined with typed throws that unify throwing and non-throwing functions under one signature form ([Announcing Swift 6](https://www.swift.org/blog/announcing-swift-6/)).
- **Maturity:**
  - Release stage: **production-used.** "We're delighted to announce the general availability of Swift 6" ([Announcing Swift 6](https://www.swift.org/blog/announcing-swift-6/)); exact Swift 6.0 release date is not stated on that page: n.a. The latest published release is `swift-6.3.3-RELEASE`, published 2026-06-30 ([swiftlang/swift releases](https://github.com/swiftlang/swift/releases)).
  - Activity in 2026: **very active** — repository last pushed 2026-09-12 with the most recent commit 2026-09-12, 70,343 stars ([swiftlang/swift](https://github.com/swiftlang/swift)).
- **Relevance to AI-agent-written code:** Data races are the single hardest class of bug for an agent to avoid, because they are invisible in the local text and only manifest under scheduling; turning them into compiler errors ([Announcing Swift 6](https://www.swift.org/blog/announcing-swift-6/)) converts an untestable property into a mechanical one. Typed throws also make an agent's error handling auditable, since the set of possible failures is in the signature rather than discovered at runtime. The countervailing factor is that strict concurrency checking is famously hard to satisfy: agents frequently produce code that is semantically reasonable but rejected under the Swift 6 language mode, and Swift's large surface area and rapid evolution mean model output often reflects Swift 5 idioms.

Strict separation of common and platform source sets ([What's new in Kotlin 2.0.0](https://kotlinlang.org/docs/whatsnew20.html)) is likewise useful, since it turns a common agent error — calling a platform API from shared multiplatform code — into a compile error instead of a link failure. ### Nim 2

- **Website / repo:** [nim-lang.org](https://nim-lang.org/), [github.com/nim-lang/Nim](https://github.com/nim-lang/Nim)

The site does not state a specific problem the language targets ([onyxlang.io](https://onyxlang.io/)).
- **Most distinctive idea:** A modernized C-family procedural language whose primary target is WebAssembly, with pipe-operator composition grafted onto imperative code ([onyxlang.io](https://onyxlang.io/)). The site does not designate a single most distinctive idea ([onyxlang.io](https://onyxlang.io/)).
- **Maturity:**
  - Release stage: **beta.** "Beta Release 0.1.13," dated 8th November 2024, preceded by "Beta Release 0.1.12" on 19th May 2024 ([onyxlang.io](https://onyxlang.io/)); `v0.1.13-beta` was published 2024-11-09 ([onyx-lang/onyx releases](https://github.com/onyx-lang/onyx/releases)).
  - Activity in 2026: **largely dormant** — repository last pushed 2026-02-26 with the most recent commit 2026-02-26 and no activity in the six months since, 691 stars ([onyx-lang/onyx](https://github.com/onyx-lang/onyx)).
- **Relevance to AI-agent-written code:** A small C-like grammar is easy for a model to emit correctly, and a WebAssembly target means generated programs run in a capability-limited sandbox by default, which is a useful containment property when executing untrusted agent output. Beyond that, Onyx offers little that specifically helps machine authorship: there is no ownership model, effect system or capability discipline to reject unsafe generated code, and with 691 stars and no commits since February 2026 ([onyx-lang/onyx](https://github.com/onyx-lang/onyx)) the corpus is far too small for reliable imitation.

### Amber

- **Website / repo:** [amber-lang.com](https://amber-lang.com/), [github.com/amber-lang/amber](https://github.com/amber-lang/amber)
- **Summary:** Amber is "the programming language compiled to Bash/Ksh/Zsh" ([amber-lang/amber](https://github.com/amber-lang/amber)), presented as "a modern, type-safe programming language that catches bugs and errors at compile time" for shell scripting ([amber-lang.com](https://amber-lang.com/)). It emphasizes exhaustive failure handling: "Amber ensures that you handle everything that could fail" ([amber-lang.com](https://amber-lang.com/)). The site notes the project won "the best Engineering Project in Technology at Wrocław University" ([amber-lang.com](https://amber-lang.com/)). The repository was created 2022-07-20, placing it in the window ([amber-lang/amber](https://github.com/amber-lang/amber)). The site does not name the maintainers or a design lineage ([amber-lang.com](https://amber-lang.com/)).
- **Most distinctive idea:** Compiling a statically typed language down to portable shell — "a language compiled to Bash" ([amber-lang.com](https://amber-lang.com/)) — so scripts get compile-time typing and mandatory error handling while still deploying as a plain shell script with no runtime dependency.
- **Maturity:**
  - Release stage: **alpha.** The most recent published release is `0.6.0-alpha`, published 2026-04-27 ([amber-lang/amber](https://github.com/amber-lang/amber)); the version string itself carries the alpha designation.
  - Activity in 2026: **active** — repository last pushed 2026-09-10 with the most recent commit on the default branch also 2026-09-10, 5,222 stars ([amber-lang/amber](https://github.com/amber-lang/amber)).
- **Relevance to AI-agent-written code:** Shell is one of the most dangerous targets for generated code — unquoted expansions, silent command failures and ignored exit codes are exactly the errors a language model reproduces from its training corpus. Amber's compile-time typing and its insistence that "you handle everything that could fail" ([amber-lang.com](https://amber-lang.com/)) convert those into compiler errors, which gives an agent a verification signal that raw Bash never provides. The counterweight is corpus scarcity: models have seen enormous amounts of Bash and almost no Amber, so an agent is likely to fall back on Bash idioms that Amber rejects. For agent-authored automation the pragmatic pattern is to let the agent target Amber and treat compile failures as the review gate.

### Neut

- **Website / repo:** [vekatze.github.io/neut](https://vekatze.github.io/neut/overview.html), [github.com/vekatze/neut](https://github.com/vekatze/neut)
- **Summary:** Neut is "a functional programming language with static memory management" ([Neut overview](https://vekatze.github.io/neut/overview.html)), maintained by the developer publishing under the handle `vekatze` ([vekatze/neut](https://github.com/vekatze/neut)). Its goal is to obtain deterministic deallocation without either a garbage collector or a Rust-style borrow checker, by making memory behaviour follow from types: it offers "predictable, type-directed memory management" ([Neut overview](https://vekatze.github.io/neut/overview.html)). The compiler "translates a type into a function for discarding and copying values of the type," which is how it arranges that "every variable is used exactly once" without forcing the programmer to write linear code by hand ([Neut overview](https://vekatze.github.io/neut/overview.html)). The type theory is stated compactly by the documentation as "The type system ≈ System Fω + ADT + recursion + box modality" ([Neut overview](https://vekatze.github.io/neut/overview.html)).
- **Most distinctive idea:** Compiling types themselves into discard/copy functions so that linearity is achieved by elaboration rather than by programmer annotation — "translates a type into a function for discarding and copying values of the type," making "every variable is used exactly once" an invariant of the generated code ([Neut overview](https://vekatze.github.io/neut/overview.html)). Borrowing is then recovered through a "box modality … achieving something like borrowing" ([Neut overview](https://vekatze.github.io/neut/overview.html)).
- **Maturity:**
  - Release stage: **pre-1.0 (0.x).** Most recent published release `0.18.1`, published 2026-05-24 ([vekatze/neut](https://github.com/vekatze/neut)).
  - Activity in 2026: **active** — repository last pushed 2026-09-09 with the most recent commit on the default branch also 2026-09-09, 1,009 stars ([vekatze/neut](https://github.com/vekatze/neut)).
- **Relevance to AI-agent-written code:** Neut's approach is unusually favourable to machine authorship among no-GC languages: the programmer never writes lifetimes, borrows or linearity annotations, because the compiler derives discard and copy behaviour from the type ([Neut overview](https://vekatze.github.io/neut/overview.html)). That removes the class of error that dominates AI-generated Rust while keeping deterministic deallocation, so an agent can write plainly typed functional code and still get predictable memory behaviour. Against that, the box modality is an unfamiliar construct with almost no public code corpus, and a 0.x language with a single primary maintainer offers little idiomatic material for a model to imitate.

### C3

- **Website / repo:** [c3-lang.org](https://c3-lang.org/), [github.com/c3lang/c3c](https://github.com/c3lang/c3c)
- **Summary:** C3 positions itself as a direct continuation of C rather than a replacement: "C3 is an evolution, not a revolution: The speed of C, shaped for modern software" ([c3-lang.org](https://c3-lang.org/)), described on the site as "The Ergonomic, Safe and Familiar Evolution of C" ([c3-lang.org](https://c3-lang.org/)). It "builds on the syntax and semantics of the C language" ([c3-lang.org](https://c3-lang.org/)) and keeps binary-level compatibility, offering "full C ABI compatibility out of the box" ([c3-lang.org](https://c3-lang.org/)). The reference implementation is the `c3c` compiler ([c3lang/c3c](https://github.com/c3lang/c3c)). The official site does not name a sponsoring organization ([c3-lang.org](https://c3-lang.org/)).
- **Most distinctive idea:** Strict conservatism about the C surface plus zero-friction interop — C3 aims to be C with modern ergonomics while retaining "full C ABI compatibility out of the box" ([c3-lang.org](https://c3-lang.org/)), so existing C code and libraries are used directly rather than through a binding layer, unlike successor languages that introduce a new object model.
- **Maturity:**
  - Release stage: **pre-1.0 (0.x), usable.** Current version is `v0.8.3`, published 2026-08-12 ([c3lang/c3c](https://github.com/c3lang/c3c)); the site likewise lists the current version as v0.8.3 ([c3-lang.org](https://c3-lang.org/)).
  - Activity in 2026: **very active** — repository last pushed 2026-09-12 with the most recent commit on the default branch 2026-09-11, 5,814 stars ([c3lang/c3c](https://github.com/c3lang/c3c)).
- **Relevance to AI-agent-written code:** Because C3 deliberately preserves C's syntax and semantics ([c3-lang.org](https://c3-lang.org/)), an agent's very large latent knowledge of C transfers almost directly, which is the opposite of the corpus problem facing most languages in this survey. The ergonomic additions replace the C idioms that generated code most often gets wrong, and full C ABI compatibility means an agent can call existing libraries without inventing binding code. The hindrance is that C3 does not add an ownership, effect or capability discipline, so the compiler cannot reject the memory-safety errors an agent will still produce; and 0.x status means the model's C reflexes will occasionally produce syntax the current compiler has changed.

### Jakt

- **Website / repo:** n.a. (no separate official site fetched), [github.com/SerenityOS/jakt](https://github.com/SerenityOS/jakt)
- **Summary:** Jakt is "a memory-safe systems programming language" developed in the SerenityOS project's GitHub organization ([SerenityOS/jakt](https://github.com/SerenityOS/jakt)). Rather than emitting machine code directly, "it currently transpiles to C++" ([SerenityOS/jakt](https://github.com/SerenityOS/jakt)), which is how it reaches an existing systems toolchain and C++ codebase. Its safety approach is a combination of strategies rather than a single discipline: automatic reference counting, strong typing, bounds checking, and "no raw pointers in safe mode" ([SerenityOS/jakt](https://github.com/SerenityOS/jakt)). The repository is explicit about its state: "NOTE: The language is under heavy development" ([SerenityOS/jakt](https://github.com/SerenityOS/jakt)), and parts of the design such as the safety analysis are marked "(Not yet implemented)" ([SerenityOS/jakt](https://github.com/SerenityOS/jakt)).
- **Most distinctive idea:** Achieving memory safety for a systems language by transpiling to C++ and layering automatic reference counting, bounds checking and a safe mode with "no raw pointers" on top ([SerenityOS/jakt](https://github.com/SerenityOS/jakt)) — safety by construction over an existing C++ toolchain rather than a new backend or a borrow checker.
- **Maturity:**
  - Release stage: **alpha / under heavy development.** "The language is under heavy development" ([SerenityOS/jakt](https://github.com/SerenityOS/jakt)) and the repository states "No releases published," so there is no version number to report ([SerenityOS/jakt](https://github.com/SerenityOS/jakt)).
  - Activity in 2026: **active but slowed** — repository last pushed 2026-08-21 with the most recent commit on the default branch also 2026-08-21, roughly three weeks before inspection, 2,988 stars ([SerenityOS/jakt](https://github.com/SerenityOS/jakt)).
- **Relevance to AI-agent-written code:** Automatic reference counting plus bounds checking is the easiest safety model for a generator to satisfy, since it requires no lifetime reasoning at all — the agent writes ordinary object-graph code and the runtime handles reclamation. Transpiling to C++ also means generated programs are auditable as C++ by existing tooling, which is useful when a human has to review machine output. But safety analysis is still marked unimplemented ([SerenityOS/jakt](https://github.com/SerenityOS/jakt)), so today the compiler cannot actually enforce the guarantee an agent would be relying on, and with no published releases and a small corpus, generated Jakt will frequently miss current syntax.

### Motoko

- **Website / repo:** [docs.internetcomputer.org/motoko](https://docs.internetcomputer.org/motoko/home), [github.com/caffeinelabs/motoko](https://github.com/caffeinelabs/motoko) (the former `dfinity/motoko` URL now redirects here)
- **Summary:** Motoko is "a high-level programming language designed for AI agents building backends for apps and services on the Internet Computer" ([Motoko docs](https://docs.internetcomputer.org/motoko/home)) — a positioning statement that names AI agents as the intended authors, not merely the intended users. Its execution model is actor-based and enforced by the language: "Every Motoko canister is an actor: an isolated unit of state and behavior that communicates with other actors through asynchronous messages" ([Motoko docs](https://docs.internetcomputer.org/motoko/home)). The language reached a stable major version in the window, with 1.0.0 recorded in the changelog on 2025-12-11 ([Motoko changelog](https://docs.internetcomputer.org/languages/motoko/reference/changelog/)). Maintenance moved organizations during the window: the canonical repository is now `caffeinelabs/motoko`, described as "Simple high-level language for writing Internet Computer canisters" ([caffeinelabs/motoko](https://github.com/caffeinelabs/motoko)).
- **Most distinctive idea:** Actor isolation as a non-optional language construct rather than a library — "Every Motoko canister is an actor: an isolated unit of state and behavior that communicates with other actors through asynchronous messages" ([Motoko docs](https://docs.internetcomputer.org/motoko/home)) — so shared mutable state across units simply cannot be expressed, and persistence of that state across upgrades is a language-level concern.
- **Maturity:**
  - Release stage: **1.0+.** Version 1.0.0 is recorded in the official changelog dated 2025-12-11, with 1.9.0 dated 2026-06-02 ([Motoko changelog](https://docs.internetcomputer.org/languages/motoko/reference/changelog/)); the most recent published release on the repository is 1.16.0, published 2026-09-09 ([caffeinelabs/motoko](https://github.com/caffeinelabs/motoko)).
  - Activity in 2026: **very active** — repository last pushed 2026-09-12, with the 1.16.0 release cut on 2026-09-09, 590 stars ([caffeinelabs/motoko](https://github.com/caffeinelabs/motoko)).
- **Relevance to AI-agent-written code:** Motoko is one of the very few languages in this survey whose maintainers explicitly frame it as a language for AI agents to write ([Motoko docs](https://docs.internetcomputer.org/motoko/home)), and the actor model supports that claim: because units cannot share mutable state and communicate only by asynchronous messages, an agent cannot introduce data races, and the blast radius of a wrong generated canister is bounded to that actor. Mandatory `await`-style asynchronous boundaries also force the concurrency structure to be visible in the source, which a reviewing agent or human can check. The friction is that upgrade-safe persistent state has non-obvious rules, which is exactly the sort of implicit constraint a generator tends to violate.

### Granule

- **Website / repo:** [granule-project.github.io/granule.html](https://granule-project.github.io/granule.html), [github.com/granule-project/granule](https://github.com/granule-project/granule)
- **Summary:** Granule is "a functional programming language based on the linear λ-calculus augmented with graded modal types" ([Granule](https://granule-project.github.io/granule.html)), a research language from the Granule Project aimed at making resource usage a checkable property of programs. Its stated ambition is generality over which resource is tracked: "The goal with Granule is to support arbitrary, user-customisable graded modalities to enable fine-grained, quantitative program reasoning" ([Granule](https://granule-project.github.io/granule.html)). The design lineage is explicitly academic, drawing on Bounded Linear Logic and "inspired by the coeffect-effect calculus of Gaboardi et al." ([Granule](https://granule-project.github.io/granule.html)). The motivating applications are resource-sensitive and security-sensitive programming, including "ensuring that private data is not inadvertently leaked" ([Granule](https://granule-project.github.io/granule.html)), and the repository summarises it as "a statically-typed linear functional language with graded modal types for fine-grained program reasoning" ([granule-project/granule](https://github.com/granule-project/granule)).
- **Most distinctive idea:** User-definable graded modalities layered on linear types, so the *quantity* and *kind* of use of every value is part of its type — "arbitrary, user-customisable graded modalities to enable fine-grained, quantitative program reasoning" ([Granule](https://granule-project.github.io/granule.html)) — rather than a fixed built-in notion of ownership or effect.
- **Maturity:**
  - Release stage: **research prototype (0.x).** Most recent published release `v0.9.6.0`, published 2024-11-22 ([granule-project/granule](https://github.com/granule-project/granule)).
  - Activity in 2026: **dormant** — the most recent commit on the default branch is 2026-07-21 and the repository was last pushed 2026-07-21, with no activity in the roughly seven weeks before inspection and no release in nearly two years, 733 stars ([granule-project/granule](https://github.com/granule-project/granule)).
- **Relevance to AI-agent-written code:** Graded types are the strongest specification mechanism in this survey: an agent could be asked to produce a function whose *type* asserts that a secret is used at most once and never leaked, and the compiler would reject a generated body that violated it ([Granule](https://granule-project.github.io/granule.html)). That makes Granule attractive as a target when the goal is machine-checkable guarantees about generated code rather than merely code that runs. In practice it hinders agents badly today: grade annotations are difficult to infer, the notation is unlike anything well represented in training data, and with a research-prototype implementation and no release since 2024 there is no corpus to imitate.

### Rust (2024 edition)

- **Website / repo:** [blog.rust-lang.org](https://blog.rust-lang.org/2025/02/20/Rust-1.85.0/), [github.com/rust-lang/rust](https://github.com/rust-lang/rust)
- **Summary:** Rust's in-window change is not a new language but a new *edition*: the announcement of "a new version of Rust, 1.85.0," dated 2025-02-20, states that "the Rust 2024 Edition is now stable!" ([Rust 1.85.0 release notes](https://blog.rust-lang.org/2025/02/20/Rust-1.85.0/)). Editions are Rust's mechanism for shipping semantics changes without breaking existing code: "Editions are a mechanism for opt-in changes that may otherwise pose a backwards compatibility risk" ([Rust 1.85.0 release notes](https://blog.rust-lang.org/2025/02/20/Rust-1.85.0/)). This qualifies as a reshaping of surface semantics on an opt-in basis rather than a routine minor release, which is why it is included here; the ownership and borrow-checking core is unchanged. Development happens in the open in the main compiler repository, described as "Empowering everyone to build reliable and efficient software" ([rust-lang/rust](https://github.com/rust-lang/rust)).
- **Most distinctive idea:** The edition mechanism itself — per-crate, opt-in semantics changes that let the language reshape surface behaviour while crates on older editions keep compiling and interoperating ([Rust 1.85.0 release notes](https://blog.rust-lang.org/2025/02/20/Rust-1.85.0/)). This is the structural feature that distinguishes Rust's evolution strategy from the successor-language approach taken by Carbon or the breaking-release approach taken by Zig.
- **Maturity:**
  - Release stage: **1.0+, production-used.** The Rust 2024 Edition shipped stable in 1.85.0 on 2025-02-20 ([Rust 1.85.0 release notes](https://blog.rust-lang.org/2025/02/20/Rust-1.85.0/)); the most recent published release at inspection is 1.98.1, published 2026-09-03 ([rust-lang/rust](https://github.com/rust-lang/rust)).
  - Activity in 2026: **extremely active** — repository last pushed 2026-09-12 with the most recent commit on the default branch 2026-09-12, 118,434 stars ([rust-lang/rust](https://github.com/rust-lang/rust)).
- **Relevance to AI-agent-written code:** Rust is the interesting control case for this whole survey. Its corpus is enormous and its compiler is an exceptionally strong verifier, so an agent gets both plentiful idiomatic material and a precise rejection signal — the pattern that makes compile-error-driven agent loops work well in practice. The cost is that borrow-checker and lifetime errors are the dominant failure mode for generated Rust, which is precisely the problem Hylo, Vale, Inko and Neut each try to design away. Editions add a subtler hazard for agents: the same source can mean different things depending on the crate's declared edition, so generated code must be matched to the target edition to compile.

- **Summary:** TypeScript had two in-window major versions. The first was announced as "Today we're excited to announce the release of TypeScript 5.0!" with the stated goal of "aiming to make TypeScript smaller, simpler, and faster" ([Announcing TypeScript 5.0](https://devblogs.microsoft.com/typescript/announcing-typescript-5-0/)); its notable surface changes were the standards-track decorators implementation, `const` type parameters, and `--verbatimModuleSyntax` ([Announcing TypeScript 5.0](https://devblogs.microsoft.com/typescript/announcing-typescript-5-0/)). The stronger in-window event is TypeScript 7, whose latest published release at inspection is `v7.0.2` on 2026-08-20 ([microsoft/TypeScript](https://github.com/microsoft/TypeScript)) — a major version reached during the window. TypeScript 5.0 release date: **n.a.** (not stated on the fetched announcement page) ([Announcing TypeScript 5.0](https://devblogs.microsoft.com/typescript/announcing-typescript-5-0/)).

- **Relevance to AI-agent-written code:** TypeScript is currently the most agent-friendly language in practical terms, for reasons that have nothing to do with novel semantics: an enormous training corpus, a type checker that runs in milliseconds without a link step, and structural typing that accepts approximately-shaped generated objects rather than demanding exact nominal types. That combination gives agent loops fast, informative rejection signals. The weakness is that its guarantees are erasable and unsound at the boundary — `any`, assertions and untyped JavaScript interop let generated code typecheck while still failing at runtime, so the checker is a weaker oracle than the ownership or effect systems elsewhere in this survey.

### ReScript

- **Website / repo:** n.a. (official site not fetched in this session), [github.com/rescript-lang/rescript](https://github.com/rescript-lang/rescript)
- **Summary:** ReScript is "a robustly typed language that compiles to efficient and human-readable JavaScript" ([rescript-lang/rescript](https://github.com/rescript-lang/rescript)). Its distinguishing claim against TypeScript is soundness rather than convenience: "No `any`, no magic types, no surprise `undefined`" ([rescript-lang/rescript](https://github.com/rescript-lang/rescript)). The project's lineage runs through the OCaml/BuckleScript ecosystem — it was "originally created by Hongbo Zhang in 2015" and is now "maintained by the ReScript community" ([rescript-lang/rescript](https://github.com/rescript-lang/rescript)). Its in-window event is the version 12 line: the repository shows release 12.3.0 dated 2026-05-20, with `v12.3.1` published 2026-08-24 ([rescript-lang/rescript](https://github.com/rescript-lang/rescript)).
- **Most distinctive idea:** A sound, fully inferring type system with no escape hatch compiling to readable JavaScript — "No `any`, no magic types, no surprise `undefined`" ([rescript-lang/rescript](https://github.com/rescript-lang/rescript)) — which is precisely the property TypeScript declines to provide.
- **Maturity:**
  - Release stage: **1.0+, production-used.** Most recent published release `v12.3.1`, published 2026-08-24; the repository lists 131 releases in total ([rescript-lang/rescript](https://github.com/rescript-lang/rescript)).
  - Activity in 2026: **very active** — repository last pushed 2026-09-12, 7,443 stars ([rescript-lang/rescript](https://github.com/rescript-lang/rescript)).
- **Relevance to AI-agent-written code:** Removing `any` and implicit `undefined` ([rescript-lang/rescript](https://github.com/rescript-lang/rescript)) turns the type checker into a genuine oracle: unlike TypeScript, an agent cannot silence a type error with an assertion and ship code that still breaks at runtime, so a clean compile carries much more information. Compiling to human-readable JavaScript also means a reviewer can inspect exactly what generated code will execute. The offsetting cost is corpus size — ReScript's public code volume is orders of magnitude smaller than TypeScript's, and its OCaml-derived syntax is far enough from JavaScript that models routinely emit invalid programs, so more compile-fix iterations are needed per accepted result.

- Repository star counts and last-commit dates are point-in-time values as of 2026-09-12 and will drift.
