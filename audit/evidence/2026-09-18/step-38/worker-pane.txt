  Decisions the brief did not cover
  1. The SIGSYS crashes were an existing Mac failure that blocked a green suite, so I
     fixed them. Two TLS brick tests (the ones "against Zig's own client") crashed on this
     Mac, already at 64982b2, because a test helper called Linux's fcntl directly. It now
     uses libc's off Linux. This is a test-only change inside bricks/tls.zig.
  2. I measured TCP_NODELAY in a Linux container (OrbStack, aarch64, cross-built mo and
     binaries), because the Mac's loopback never shows Nagle's delayed-ACK wait. The Mac's
     before/after is in RESULTS.md too.
  3. The bulk windows use a new client, bench/step38/window-dial.mo, instead of step 37's
     measure.py, which only knows two windows of 64. It sends 3,200 lines; windows of 256
     send 3,072 (whole windows only).
  4. duplex.mo's main times each leg itself and prints "under a second: true/false", so
     the corpus checks the one-second bound under both runtimes. If a heavily loaded
     machine ever pushes a leg past one second, that line will flake.
  5. The Busy checks in duplex.mo are sequenced by pausing main in an accept with a
     timeout on an idle listener. That lets the process it just sent to reach its wait
     first; without the pause the second write raced and came back Ok.
  6. read_back is recursive, because the corpus forbids a for around read_line in
     examples.
  7. The handshake still flushes its flight before reading. A TLS 1.3 peer reads each
     flight before sending its next, so a handshake read never waits on its own write. The
     part of the brief's "an accept's handshake read proceeds" that could apply is that
     nothing else writes to the socket mid-record during a handshake.
  8. close now skips close_notify while a flush is halfway through a record, because it
     would cut that record.
  9. The abuse peer is Python's ssl (OpenSSL 3.6.4), not /usr/bin/openssl, which on this
     Mac is LibreSSL 3.3.6.
     - Alerts during the handshake go in the clear. At the server's flight state the alert
       is OpenSSL's own unknown_ca, which it sends in the clear.
     - Mid-flight the client gets a clear alert, because OpenSSL has already switched to
       its application keys and can't write one under the handshake keys.
     - After the handshake, alerts are encrypted by OpenSSL itself (bad_record_mac,
       provoked by feeding it a record it can't open).
  10. After the handshake, the expected answer to a close_notify is the end of the stream
      (None), and to a fatal alert or reset it is Closed.
  11. The suite is run under the brief's guard and 2400 s timeout, not the brief's timeout
      2400; the step 37 corpus tests that start their own processes inside the suite
      remain unguarded as they were.
