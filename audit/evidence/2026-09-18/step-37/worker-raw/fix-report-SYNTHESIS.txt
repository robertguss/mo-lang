== What changed and why ==
1. Closed for a peer's alert (both runtimes). The brick's peerAlert records the alert and sets phase=broken, but
   it returns no error, so mo_tls_feed returns ok (the alert was read, not answered). The socket handshakes
   (net.zig Net.handshake, mo_rt.c tls_handshake) then read again and got the stream's end (EOF) -> Closed.
   The fixture path already asked mo_tls_read after each pump, which is why it gave Handshake. Fix: both socket
   handshakes now ask the engine before each read: mo_tls_read(t, NULL, 0) == failed -> flush (nothing, or this
   side's alert) and refused(t) (Handshake, or Untrusted when this client refused the chain); == closed
   (close_notify / user_canceled) -> Closed. No new export: mo_tls_read's existing failed/closed answer is what
   tells a peer's fatal alert from the stream's end.
2. The binary's SIGSEGV: a double free in mo_rt.c's tls_handshake. It sets c->tls = t for the whole handshake. When
   a read broke (read() < 0, e.g. ECONNRESET from the OpenSSL client that refuses the chain and aborts with the
   server's flight unread, or any RST mid-hello), tls_feed called net_close -> net_release, which frees c->tls;
   tls_handshake then called mo_tls_conn_free(t) again. With the brick's heap corrupted, the next connection's
   engine crashed in mo_tls_feed (gdb backtrace: mo_tls_feed <- tls_feed <- tls_handshake <- mo_r_TlsServer_accept,
   the wire holding the next client's ClientHello). A new tls_give_up frees the engine only while c->tls still
   holds it, then closes. Confirmed on the old runtime: a binary tls-echo died after a single raw client that
   sent 8 bytes of a hello and reset (the next connect was refused); fixed, three such clients then a good client
   each echo. mo run never had it: net.zig puts the engine on the Conn only once the handshake is done.
   The alert fix (1) also moved the probe's case off the broken-read path, but (2) is fixed on its own.
3. Tests. Brick (tls.zig): "an alert where a hello belongs: a fatal one leaves the server's read failed,
   close_notify closed" (unknown_ca, protocol_version -> failed; close_notify, user_canceled -> closed; feed ok,
   alert_from_peer, nothing to send back), and expectRefused (every chain refusal, i.e. a fatal alert the client
   sends the server after the server's flight, mid-handshake) now also checks the server's mo_tls_read is failed.
   Corpus (corpus.zig): "a fatal alert where a hello belongs is Handshake and a reset mid-hello is Closed, under
   mo run and in a binary, and the server takes the next connection": a Mo TLS server written into a tmp dir,
   run both ways over real sockets, five raw clients (alert, reset, alert, reset, alert), expects
   Handshake/Closed/Handshake/Closed/Handshake and exit 0. On the old net.zig and mo_rt.c it fails with Closed x5.
