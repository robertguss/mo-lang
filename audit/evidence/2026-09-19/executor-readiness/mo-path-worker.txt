  Transport and adapter contract

  Existing provider wire format is immediately reusable:

  - POST /complete, content-type: application/json, x-run: <run-id>: model.mo:143.
  - Request: {"goal": "...", "tools": ["..."], "transcript": [...]}: model.mo:101.
  - HTTP 200 response: either {"tool":"…","args":{"key":"string"},"tokens":n} or
    {"done":"…","tokens":n}.

  - Arguments must all be strings; tokens must be present and a nonnegative integer:
    model.mo:182, model.mo:213.

  - One tool per response. The adapter must translate provider messages/tool schemas into this
    representation; it must not execute tools or own the loop.

  Proposed execution protocol, not existing functionality: a configured, trusted local HTTP
  endpoint accepting a versioned request containing run/call IDs, an opaque workspace ID,
  operation/arguments, remaining timeout, and output bound. Return a structured outcome
  distinguishing success, refusal, failure, timeout, cancellation, and uncertain completion,
  with nullable exit status, stdout/stderr, truncation flags, and observed duration. Bind
  workspace and policy outside model-supplied arguments. Never automatically replay a command
  after an ambiguous transport failure.

  Use a separately started adapter. Mo’s documented prelude exposes neither subprocess execution
  nor stdin. It does expose arguments, stdout/stderr, HTTP, and TCP line I/O: toolchain/
  PRELUDE.md:263, :280, :304. Thus:

  - CLI arguments/config file → Mo, JSONL → stdout: viable.
  - HTTP request/response adapters: smallest change.
  - TCP JSONL: possible using Conn.read_line/write.
  - Bidirectional stdio adapter or spawning an adapter from Mo: unavailable through the
    documented language surface.

  The prelude explicitly states its tables are exhaustive (PRELUDE.md:3). Mo processes are not
  OS subprocesses.
