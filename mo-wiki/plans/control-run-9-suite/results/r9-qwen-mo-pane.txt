 # Program 1, change 1: scheduled jobs, retry backoff, and the `tries` rename

 A change to `jobq` as specified in `01-job-queue.md`, the first change any program in this
 project has received after it was finished. Written by Claude (Fable) in session 7, 15 Sep
 2026, for control run 8, the maintenance round: a fresh agent that has never seen the
 program gets the finished program, this page, and the instruction that the tests must pass
 and the service must keep its durability. Everything `01-job-queue.md` says still holds
 unless a line below changes it. The shape is a product ticket: a producer wants to delay a
 job, a worker wants a failed job to wait before it is tried again, an operator wants a dead
 job back, and the API's counters get the names the team uses.

 ## What changes, in one screen

 1. A job may be **scheduled**: created with a delay, or put back with a backoff after a
 fail, it waits until its `run_at` and is queued at the next look after that.
 2. A dead job may be **retried** through a new route, which puts it back in its queue with
 its tries reset.
 3. `attempts` and `max_attempts` are renamed **`tries`** and **`max_tries`** everywhere the
 service speaks: requests, responses, listings, and the records it writes.
 4. **A log the old service wrote still opens.** The rename and the new fields change the
 record; the store must replay a log written before this change, read the old names, and
 after `compact` hold only the new ones.

 The store's log format is SET key value\n / DEL key\n. The value is the job's JSON. So the
 rename of attempts->tries etc. happens at the job.mo level (JSON), not the store level. The
 replay of old log: the store replays the log and the value is a JSON string, which is
 decoded by job.decodded. So to replay a log that the old service wrote, the decoded function
 in job.mo must read old names (attempts, max_attempts) and treat missing backoff_ms as 0,
 and missing run_at as no scheduled state.

 Let me think about the change conceptually:

 1. Job fields rename: attempts -> tries, max_attempts -> max_tries in job.mo and throughout.
 Plus new fields backoff_ms (0 to 3,600,000, default 0, fixed at creation) and while
 scheduled, run_at.
 2. New state Scheduled:
     - created with delay_ms = 0 -> queued
     - created with delay_ms > 0 -> scheduled, run_at = created_at + delay_ms
     - scheduled -- run_at reached, at next look --> queued
     - on fail/run-out, if tries < max_tries and backoff_ms == 0 -> queued; if tries <
 max_tries and backoff_ms > 0 -> scheduled, run_at = now + backoff_ms
     - dead -- retry --> queued, tries = 0
 3. Retry route: POST /jobs/{id}/retry -> 200 {job} | 409 when not dead | 404
 4. API:
     - Create: add delay_ms?, backoff_ms? (default 0)
     - attempts/max_attempts renamed to tries/max_tries in responses.
     - A request that still says attempts or max_attempts is 400.
     - /health now includes "scheduled".
     - Listing state may be "scheduled".
 5. Durability: scheduled-to-queued move written to store before response.
 6. Replay of old log: decoded reads old names. Old log has attempts/max_attempts. New log
 has tries/max_tries/backoff_ms. After compact, only new names.
