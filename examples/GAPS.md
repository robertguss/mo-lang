# Corpus gaps

Places where a program needed something `spec/grammar.md` and `spec/design-v0/04-syntax.md` do not define. One line per gap: the first file that needed it, what was missing, the default the corpus uses. Robert decides; the corpus only records. Gaps settled by the Session 5 decisions at the foot of `grammar.md` are gone from this list, and the files follow the decisions.

- `types/generics.mo`: no stdlib trait names exist (pick 15's `Comparable` is only an example). Default: the bound names a trait declared in the same file.
- `recipes/rate-limiter.mo`: chapter 6 uses `Limiter`, `ClientId`, and `tokens` without declaring them, and nothing names a type whose fields the implementer chooses. Default: `type ClientId = String` in the module; `tokens` and `limiter` are body-less signatures in the recipe; `Limiter` and `l.capacity` stay undeclared, as in chapter 6. The checker reads an undeclared type in a recipe signature as opaque (the implementer chooses its fields), so a field read on it is not checked at tier 1.
- `effects/timeout.mo`: grammar gives `Fs.read` the error type `FsError` but never lists its variants, and `try` needs them to match the caller's error enum. Default: `FsError` is `Missing(path: String) | Timeout`, marked corpus-only in `toolchain/PRELUDE.md`. Step 17 adds `NotText` from design-v0/09, for a file a row that gives a `String` finds is not UTF-8.
- `payments/refund.mo`: chapter 4 takes `Charge`, `ChargeId`, `Money` from `Payments.Ledger`, which is not written, and also uses `CardNumber`, `RefundRequest`, `RefundCompleted`, `RefundFailed`, `t0`, `db.find_charge`, `db.save_charge`, `Charge.fixture`, `charge.refunded?`, `Money.cents`, and `Money.zero` without declaring them. Default: corpus-only stand-ins in `toolchain/PRELUDE.md`. `find_charge` and `save_charge` fail with `LedgerError`, whose one variant is `Timeout`, because `try` in `refund` can re-tag only variants `RefundError` also has. Nothing says what a `Ledger.fixture()` holds. Default: it finds every id as an unrefunded charge of 10_000 captured at `Time.fixture()`, and every save succeeds, so the queue test's refunds go through.
- `payments/refund.mo`: the corpus copy differs from chapter 4 in six places. Three are rules the toolchain enforces. Its first test binds `result = ...`, but `result` is a keyword (grammar §1), so the copy names it `outcome`. `within_window?` and `refund` each have a `requires` with no `test rejects` (MO0311), so the copy adds one `test rejects` for each. Its `verified:` line is written by hand (MO0317), so the copy leaves it off. The fourth is a false property: `mo test` found, on the first seed, a charge that is already refunded, which `apply_refund` answers with `AlreadyRefunded`. The copy's guard adds `!charge.refunded? and`. The fifth and sixth come with processes (step 4): `RefundQueue` gains `message Done : UInt32` so a test can read `done` with an `ask`, and the copy adds the test that starts the queue, sends `Enqueue` twice and `Drain`, and asks for `Done`. Its ask waits `within: 1_000.ms` (step 9): under `mo test --sim` a ledger call that times out waits its whole 200 ms, so a 100 ms ask passed only in a world where no call fails; the drain's four calls wait at most 800 ms.
- `types/generics.mo`: the grammar has no syntax that declares a type parameter; `fn first(xs: List(T))` just uses `T`. Default in the checker: an undeclared one-letter type name in a function signature is a type parameter of that function; anywhere else it is an unknown type.
- `programs/echo/main.mo`: nothing repeats until something happens, such as a connection's end of stream; `for` goes over a range or a list, and the interpreter builds a range's whole list before its first iteration, so `for _ in 0..1_000_000` costs a million elements every time it starts (about 15 ms under `mo run`, once per connection). Default: the worker's loop is `for _ in 0..10_000` with `break`, so a connection is served for at most 10,000 lines. Program 3's workers meet the same gap. Step 20: the runtime owns that loop: `listener.serve` and `conn.lines` deliver each connection and each line as a message, so echo's worker takes `Line` messages and nothing repeats around `accept` or `read_line`.
- `stdlib/maps.mo`: design-v0/09 gives `Map(K, V)` and `Set(T)` no literal syntax (step 8 left literals to Robert). Default: a map is built from `Map.new()` with `set`, `update`, or `List.group_by`, and a set from `Set.new()` with `add`.
- `programs/kv/server.mo`: the echo gap above. Default: a worker serves a connection in two nested ranges of 10,000, so at most 100 million lines, and `kv serve` accepts at most 100 million clients before it returns. Step 20: kv serves its listener into its listening process and reads each connection into its worker, so neither range is left, and `kv serve` serves until it is stopped.
- `recipes/store.mo`: nothing checks an implementation against its recipe. Chapter 6 says the compiler checks the result against the recipe (shape, tests, and capabilities under `needs`), but the toolchain only checks a recipe's own signatures against its `needs` line (MO0406) and skips its tests; no syntax names the recipe a module implements, and no command runs a recipe's tests against a module. Default: `programs/notes/limits.mo` and `programs/notes/store.mo` copy their recipe's tests by hand, under a comment saying so, and match its signatures by eye. Step 19: `mo check --recipe Module.Recipe file.mo` holds an implementation to its recipe's signatures and runs the recipe's tests and nevers against it, and the corpus test runs it for each file whose first lines say `# recipe: Module.Recipe`, so `limits.mo` and `store.mo` no longer copy the tests.
- `recipes/store.mo`: `recipe` holds only signatures and tests (grammar §11), so a recipe cannot carry a `never`, and chapter 6 says nothing of where a recipe's nevers go. Default: the recipe module declares them at its head, over structs it declares beside the recipe, and the implementation copies both. Step 19: a recipe holds `never` blocks after its signatures; `recipes/store.mo` keeps its two there, and `programs/notes/store.mo` keeps the same two for its own runs, which `mo check --recipe` holds to be the recipe's line for line.
- `programs/notes/server.mo`: a capability reaches a process only as a start argument, so an `Exchange` can be handed to a worker only by starting a new process for it; no message can carry one to a worker already running. With processes never freed (`programs/notes/TOOLCHAIN-BUGS.md`, bug 1), a pool is the only bounded shape and it cannot be written. Default: the acceptor answers each exchange itself. Step 20: a message may carry a capability its `message` line declares, and `HttpListener.serve` hands each exchange to the acceptor as `Accepted(exchange: Exchange)`; notes still answers in the acceptor, one exchange at a time.
- `programs/notes/main.mo`: the echo gap above. Default: `notes serve` hands its acceptor at most 100 million exchanges in two nested ranges of 10,000. Step 20: `notes serve` serves its listener into the acceptor, with no range.
- `programs/notes/main.mo`: `Fs` has no row that makes a folder, so `notes check` cannot copy a fixture folder somewhere to write. Default: as `kv check`, it reads `data/demo/notes.log` read-only and appends its changes to `notes.check.log` beside it, removed before and after.
- `programs/notes/main.mo`: a program run under `mo run` has no way to fix its clock, and every note carries two timestamps, so a transcript of real requests is not the same twice. Default: `notes check` replaces the values of `created_at`, `updated_at`, `uptime_ms`, and `retry_after_ms` in what it prints with `<name>`; the client prints them as they came.
- `programs/notes/service.mo`: `or` gives a default only for an `Option`; a `Result` needs a `case` to fall back (`open(fs, dir) or fresh()` is MO0206). Default: a `case` with an `Error(_)` arm. Step 19: MO0206 there now says that `or` is for an `Option` and to write that `case`.
- `programs/jobq/job.mo`: `state` is a keyword (and so is `old`), so no struct can have a field named `state`, and `Json.encode` of a struct cannot write the `"state"` key the job queue's API names; and `Json.decode` reads every number as a `Float64` with no float-to-integer row (design-v0/09, "Not in this step"). Default: a job's field is `status`, its JSON is written by hand from `Json.encode` of each string and time, and a count is read back as `value.to_string(0).to_u64` once `value.round(0) == value`. Step 22: `json.to_i64` gives a `Number`'s whole value below 2^53, and `job.mo` reads counts through it; `state` stays a keyword.
- `programs/jobq/main.mo`: a capability is never returned (MO0403) and a struct cannot hold one, so the 1,200 connections `jobq check` holds open for its `crowd` line cannot be opened by a function of their own; with the six-parameter law, `ran` and `check` take their capabilities one by one. Default: the loop that plays the script opens the crowd into a `var` list it keeps until the script ends, one `for` inside another.
- `programs/jobq/books.mo`: `Fs.fixture()` answers `list` on a folder that is not there with `Ok([])`, as its row says, where the real `Fs` answers `Missing(".")`, so no test can show `jobq serve` refusing a missing folder; the corpus run `serve data/nowhere` shows it instead. Step 22: the fixture answers `Missing(".")` as the real `Fs` does, and `books.mo` has the test.
- `programs/jobq/server.mo`: a deadline cannot be derived from an enclosing one, so the worker's `ask` of the queue waits a literal 60 seconds chosen to outlast the literals of the Fs calls one message can make (a rewrite of the log, 20 and 5 seconds, then an append and a size, 5 and 5), and `main`'s `Open` waits 660 seconds to outlast the replay's 600, 10, and 10; nothing checks the sums, and a Fs literal raised later breaks them silently. Default: the sums are written in comments beside the literals; the report counts them as derived.
- `programs/jobq/moves.mo`: Mo has no delayed send and no timer, so nothing fires when a lease runs out. Default, and the spec's rule: a lease is a deadline the queue checks at its next look (a lease request, an ack, a fail, a read, a listing, or the listener's `Idle`, which the acceptor turns into a `Sweep`).
